# ТЗ: вход на сайт через бота академии

> Ученик входит на nmnh.trade одноразовым паролем, который выдаёт бот академии.
> Документ описывает контракт между двумя машинами, модель данных, защиту и
> порядок внедрения.
>
> Статус: к реализации. Ничего из описанного ещё не написано.

## 1. Зачем

Сейчас вход один: **по WEEX UID**. Ученик вводит UID, платформа проверяет его у
биржи, находит одобренного ученика и отправляет шестизначный код в Telegram
через сигнального бота ([auth.py:90](../../backend/api/auth.py)).

У этого пути два ограничения.

**Нужен UID.** Ученик академии, который ещё не завёл счёт на бирже, войти не
может вовсе — а учится он уже сейчас, и монеты за пройденные модули ему
начисляются ([nmnh_platform.py в боте](#4-что-уже-есть)).

**Код доставляет платформа.** Она должна дозвониться до Telegram сама. Бот
академии живёт на другом удалённом столе, и связь между машинами уже рвалась —
именно поэтому начисление монет там сделано с очередью досылки.

Вход через бота академии снимает оба: **идентификатор — Telegram, а не биржа**, и
**код едет от бота к платформе, а не наоборот**. Платформе никуда звонить не
надо.

## 2. Как это выглядит для ученика

1. На странице входа он выбирает «Войти через Telegram».
2. Открывает бота академии и жмёт кнопку «Войти на сайт» (или команду `/login`).
3. Бот отвечает одноразовым паролем: `K7M4-QP2X`, срок 5 минут.
4. Ученик вводит пароль на сайте и попадает в кабинет.

Вход по WEEX UID остаётся как был: это не замена, а второй путь.

## 3. Почему так, а не иначе

**Пароль набирают руками, а не переходят по ссылке.** Ссылка вида
`t.me/bot?start=login_<nonce>` короче в одно нажатие, но требует, чтобы сайт и
Telegram были на одном устройстве. Ученик чаще открывает сайт на компьютере, а
бота держит в телефоне. Пароль работает в обоих случаях.

**Код запрашивает бот, а не сайт.** Обратный порядок (сайт просит платформу,
платформа шлёт в Telegram) уже реализован для UID и требует, чтобы платформа
достучалась до бота. Здесь наоборот: бот сам приходит за паролем по тому же
каналу, по которому уже носит начисления монет. Одна связь вместо двух.

**Пароль опознаёт ученика целиком.** На сайте не спрашивается ни Telegram-ник,
ни номер: только пароль. Иначе ученик обязан помнить, каким именем он записан, а
Telegram-ник ещё и меняется.

Из этого следует требование к длине пароля — см. [§7](#7-защита).

## 5. Контракт

Две ручки. Первая — для бота, закрыта сервисным ключом. Вторая — публичная, для
страницы входа.

### 5.1. Бот просит пароль

```
POST /api/auth/tg/code
X-Service-Key: <SERVICE_API_KEY>
Content-Type: application/json

{ "tg_id": 123456789, "username": "kaktotakxm" }
```

Ответ `200`:

```json
{ "code": "K7M4-QP2X", "expires_in": 300 }
```

Отказы:

| Код | Когда | Что делает бот |
|---|---|---|
| `401` | Сервисный ключ не тот | Пишет в лог, ученику — «вход временно недоступен» |
| `403` | Ученик не найден или не одобрен | Показывает: «обратитесь к наставнику» |
| `429` | Слишком часто с этого `tg_id` | Показывает, через сколько можно повторить |
| `503` | `SERVICE_API_KEY` не задан на платформе | То же, что `401` |

**Повторный запрос до истечения срока отдаёт тот же пароль,** а не заводит
новый. Ученик нажал кнопку дважды — он ждёт один пароль, а не гадает, какой из
двух рабочий. Срок при этом не продлевается.

### 5.2. Сайт проверяет пароль

```
POST /api/auth/tg/verify
Content-Type: application/json

{ "code": "K7M4-QP2X" }
```

Ответ `200` — та же пара токенов, что и у существующего `/api/auth/verify`
(`TokenPair`): дальше кабинет не отличает, как ученик вошёл.

Отказы:

| Код | Когда |
|---|---|
| `400` | Пароль не подошёл: не существует, истёк или уже использован |
| `429` | Перебор: слишком много попыток с этого адреса |

Причину неудачи **не уточняем**. «Пароль истёк» и «пароля нет» — подсказка тому,
кто перебирает.

## 6. Модель данных

Новая таблица `tg_auth_codes` рядом с существующей `auth_codes`. Не расширение
существующей: там ключ — `weex_uid`, здесь `tg_id`, и смешивать два способа
входа в одной таблице значит однажды выдать токен не тому.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | PK | |
| `tg_id` | `BigInteger`, индекс | Кому выдан |
| `code_hash` | `String(64)` | SHA-256 пароля, не сам пароль |
| `expires_at` | `DateTime(tz)` | Срок |
| `used_at` | `DateTime(tz)`, null | Когда предъявлен |
| `attempts` | `Integer` | Сколько раз ошиблись при вводе |
| `created_at` | `DateTime(tz)` | |

**Хранится хеш, а не пароль.** Пароль живёт пять минут, но база живёт годами, и
утечка дампа не должна означать возможность войти. Хеш здесь без соли намеренно:
пароль случаен и короткоживущ, а поиск по хешу должен быть индексируемым.

Колонки добавляются автоматически при старте — общим проходом в
[core/db.py](../../core/db.py), как это уже работает для `chart_shots`.

## 7. Защита

**Длина пароля.** Восемь символов из алфавита без похожих начертаний
(`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, без `I`, `O`, `0`, `1`) — это 32⁸ ≈ 10¹²
вариантов, около 40 бит. Шесть цифр, как в существующем входе, здесь не годятся:
там код привязан к введённому UID, а тут проверяется сам по себе — подходит
любой живой пароль любого ученика, и миллион вариантов перебирается за часы.

Показывается с дефисом посередине (`K7M4-QP2X`), при проверке дефис и регистр не
важны: набирают руками, и человек не обязан помнить, где черта.

**Ограничение частоты.**

| Что | Предел |
|---|---|
| Выдача пароля одному `tg_id` | 3 в 10 минут |
| Проверка пароля с одного адреса | 5 в минуту, 30 в час |
| Ошибок на один пароль | 5, дальше он сгорает |

Существующий `AuthRateLimitMiddleware` покрывает весь префикс `/api/auth`; для
`/tg/verify` нужен отдельный, более узкий предел — вход по UID гораздо реже
подвергается перебору.

**Одноразовость.** Успешная проверка проставляет `used_at` в той же транзакции,
что и выдача токенов. Второй раз тот же пароль не сработает даже при гонке
двух одновременных запросов — условие `used_at IS NULL` идёт в сам `UPDATE`.

**Уборка.** Просроченные записи удаляются при каждой выдаче нового пароля: своей
задачи по расписанию ради этого заводить не нужно.

**Сервисный ключ.** Тот же `SERVICE_API_KEY`, что и у начисления монет, и та же
сверка через `secrets.compare_digest`. Отдельный ключ завести можно, но он не
добавит защиты: обе ручки доступны одному и тому же боту.

**В логи пароль не пишется.** Ни в боте, ни на платформе. В логе — только `tg_id`
и факт выдачи.

## 8. Кто попадает в кабинет

Пароль выдаётся, только если в базе платформы есть **одобренный активный**
ученик с этим `tg_id`.

Ученика, которого нет, платформа **не заводит сама**. Академия и платформа —
разные круги: в академию попадают свободно, а в кабинет с терминалом и деньгами
пускает наставник. Автоматическое заведение стёрло бы эту границу молча.

Для перехода предусмотрен флаг `TG_LOGIN_AUTOCREATE` (по умолчанию выключен).
Включённым он заводит ученика по `tg_id` со статусом «ждёт одобрения» — тот
получает отказ на входе, но появляется у наставника в списке. Это отдельное
решение, и принимать его отдельно.

## 9. Поведение при обрывах

**Платформа недоступна.** Бот не выдаёт пароль и говорит об этом прямо. Очередь
досылки, как у монет, здесь вредна: пароль, доехавший через полчаса, ученику уже
не нужен, а живёт он пять минут.

**Бот недоступен.** Вход по WEEX UID продолжает работать. Страница входа
показывает оба пути и не делает Telegram единственным.

**Ученик потерял пароль.** Просит новый: до истечения срока придёт тот же, после
— новый.

## 11. Проверки

Тестами закрывается то, что ломается молча.

**Платформа:**

- пароль выдаётся только одобренному ученику; неодобренному — `403`;
- повторный запрос до истечения срока отдаёт тот же пароль и не продлевает его;
- истёкший пароль не подходит;
- использованный пароль не подходит второй раз;
- два одновременных запроса с одним паролем: токены получает ровно один;
- дефис и регистр при вводе не важны;
- в базе лежит хеш, а не пароль;
- перебор упирается в предел и получает `429`;
- чужой сервисный ключ получает `401`, отсутствующий на платформе — `503`.

**Бот:**

- платформа недоступна — ученик видит понятный отказ, а не молчание;
- пароль не попадает в логи.

**Руками, на боевом:** вход с компьютера при боте в телефоне — тот случай, ради
которого выбран пароль, а не ссылка.

## 12. Что дальше

**Фаза 2: вход одним нажатием из мини-аппа.** У бота уже есть проверка подписи
`initData` (`telegram_init_data.py`). Мини-апп академии может открывать кабинет
без пароля вовсе: подпись Telegram доказывает, кто пользователь, надёжнее
набранного вручную кода. Это отдельная работа и отдельный контракт — здесь она
упомянута, чтобы модель данных ей не мешала.

**Связывание с биржей.** Ученик, вошедший через Telegram и позже заведший WEEX
UID, должен остаться одной записью, а не двумя. Связка идёт по `tg_id`, который
у обоих способов входа один и тот же, — но проверить это отдельным тестом при
внедрении обязательно.
