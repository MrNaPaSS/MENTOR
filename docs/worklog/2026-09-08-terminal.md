## 1. Комиссия: главная находка

### Как обнаружилось

Трейдер сверил журнал с приложением биржи:

| Сделка | Биржа | Журнал | Разница |
|---|---|---|---|
| ETHUSDT | +90.7024 | +98.71 | 8.01 |
| BTCUSDT | +23.3369 | +27.34 | 4.00 |

Разница не совпадала ни с процентом от прибыли, ни с фиксированной суммой. Зато
она составляла **ровно одну и ту же долю от комиссии** — 0.361 в обеих сделках.
Ошибка, пропорциональная комиссии, а не прибыли, — это ошибка в комиссии.

### Проверка

Брутто сошлось с биржей до копейки:

```
ETH: (2488.80 − 2482.71) × 20.155 = 122.74   журнал: 98.71 + 24.08 = 122.79
BTC: (79114.3 − 78990.0) × 0.3164 =  39.33   журнал: 27.34 + 12.02 =  39.36
```

Значит прибыль считалась верно. Настоящая комиссия — разница брутто и того, что
пришло на счёт: 32.04 и 15.99. В журнале стояли 24.08 и 12.02 — **ровно 0.75 от
настоящей**. Одинаковая доля на двух разных монетах, а потом и на всех четырёх
сделках при пересчёте: три ноги из четырёх.

### Причина

Флаг «комиссия названа» был один на весь отчёт об исполнениях:

```python
if paid is not None:
    has_fee = True          # ← на весь отчёт
    fee += abs(paid)
...
if not has_fee and turnover > 0 and taker_fee > 0:
    fee = turnover * taker_fee   # ← запасной расчёт отключён целиком
```

Позиция закрывалась тремя частями (доли целей 30/50/20). Про среднюю — половину
объёма — отчёт комиссию не назвал. Одного названного исполнения хватало, чтобы
отключить досчёт для всех остальных, и комиссия этой части просто терялась.
Четверть общего оборота (вход 100% + выходы 100%, из них потеряно 50%) —
отсюда и ровно 0.75.

### Решение

Оборот считается раздельно — с названной комиссией и без. Молчащие исполнения
досчитываются **по ставке самих названных**, а не по справочной ставке
инструмента.

Почему не по справочной: у этих сделок она 0.08%, а биржа удержала 0.032%.
Досчёт по справочной дал бы втрое больше удержанного и записал бы убыток,
которого не было. Ставка, выведенная из соседних исполнений той же сделки, дала
32.10 против настоящих 32.04.

Справочная остаётся запасным вариантом на случай, когда сравнивать не с чем —
когда не названо ничего.

### Проверка после исправления

Пересчёт на живых данных совпал с биржей:

```
ETHUSDT: итог +98.71 → +90.70, комиссия 24.08 → 32.08, цели 3 → 2
BTCUSDT: итог +27.34 → +23.34, комиссия 12.02 → 16.01, цели 3 → 2
```

## 2. Цели: счётчик, который умеет только расти

В журнале у сделки, взявшей две цели и выбитой стопом в безубыток, стояли три
цели. Число бралось так:

```python
hit = max(hit, targets_reached(trade, exit_price))
```

`max` может только поднять. Счётчик ведёт сопровождение, а стоп уносит с биржи
все оставшиеся цели разом — по их исчезновению сделка выглядит забравшей всё.
Проверка ценой выхода это не чинила: она шла через `max` и опустить счётчик не
могла.

Теперь цели считаются по самим исполнениям (`takes_from_fills`): до какой цели
дошла хоть одна продажа лонга, та и взята. Вход в счёт не идёт — иначе цель
«брала» бы себя ценой входа.

**Опустить счётчик вправе только полный отчёт.** Список исполнений приходит
окном — последние сто и не раньше времени входа. Если входа в нём нет, окно
застало сделку с середины, взятая цель могла остаться за краем, и счёт по такому
отчёту занизил бы число целей вместо того, чтобы поправить завышенное. Тогда
доверяем счётчику: ошибиться в его сторону безопаснее.

Это правило нашлось не сразу — первая версия ломала существующий тест
`test_journal_entry_keeps_the_targets_of_the_trade`, и он был прав.

## 3. Пересчёт старых записей

`backend/trading/recount.py` — разовый скрипт. Журнал хранит итог, а не способ
его получить, поэтому записи, сделанные до исправления, сами себя не перепишут.

```bash
python -m backend.trading.recount            # показать, ничего не меняя
python -m backend.trading.recount --apply    # записать
python -m backend.trading.recount --days 3   # за последние три дня
```

Осторожность важнее полноты:

* по умолчанию не пишется ничего;
* сделку, исполнений которой биржа уже не помнит, не трогаем — записать по
  пустому отчёту ноль значило бы стереть настоящую сделку;
* исполнения отбираются по времени самой сделки с запасом в минуту: за день по
  одной монете их бывает много, и общий отчёт сложил бы в одну запись результат
  нескольких.

**Ограничение.** У WEEX история исполнений не бесконечна. Сделки, которые она уже
не отдаёт, останутся со старыми числами.

### Грабли при запуске

Скрипт запускают отдельно от сервера, и он трижды спотыкался о то, что сервер
делает при старте:

| Симптом | Причина | Решение |
|---|---|---|
| `WEEX_KEYS_SECRET не задан` | `.env` читает `backend/config.py` при импорте | Импортируем его ради побочного действия |
| `unable to get local issuer certificate` | На Windows Python не достаёт до системного хранилища | Корневые сертификаты из `certifi`, как в `backend/api/trading.py` |
| «Всё сходится, менять нечего» при четырёх ошибках | Несостоявшиеся сделки не считались | Считаются отдельно и называются вслух |

Проверку сертификата не отключали: в этих запросах ходят ключи от денег ученика.

## 4. Разметка ждущей заявки

Разметка — бокс, стоп и цели — вспыхивала сама: курсор шёл к ценовой шкале
справа, задевал невидимую полоску захвата, и поверх идущей сделки появлялись
чужие стопы с целями.

Итоговое поведение:

* **наведение на ярлык** «ждём вход» — предпросмотр, пока курсор на плашке;
* **нажатие** — закрепляет разметку насовсем, дальше уровни правят руками;
* на самих линиях наведения нет — полоски захвата невидимы и тянутся во всю
  ширину.

Полоски захвата у незакреплённой заявки оставлены только на лимитке: под стоп и
цели они заводились, хотя тех на графике нет, и по экрану ползли цветные полосы
там, где линий не видно.

Отдельно: **протяжка строго вбок** засчитывалась как нажатие — цена не менялась,
а по одной цене клик от протяжки не отличить. Теперь различаем по пройденному
пути, с запасом в три точки на дрожь руки.

## 5. Ряд свечей

Минуты без единой сделки лента пропускает, и в ряду появлялась дыра: за баром
12:03 сразу шёл 12:07, и график врал о том, сколько времени заняло движение.
Пропуски дорисовываются плоскими свечами по последней цене — так же, как их
отдаёт биржа, — но не больше двух часов: дальше это не пропуск, а мёртвая лента.

Свеча чужого таймфрейма, приезжающая между переключениями, отсеивается по сетке:
пятиминутка кратна минуте, и одним «больше последнего» её не отличить.

## 6. Радио

Плеер живёт в `webapp/lib/radio.ts` — **один на всё приложение**. Кнопок две: в
шапке кабинета и в полном экране терминала. Свой `<audio>` у каждой означал бы
вторую станцию поверх первой.

Готовый виджет радиостанции не встраивался: он приносит свой CSS, свою вёрстку и
баннер со ссылкой наружу. Взяты только адреса потоков.

* **Пульс** — линия стоит на месте, шевелится середина. Форма волны с ленты
  умножается на оконный множитель: на краях он равен нулю, поэтому первая и
  последняя точка прибиты к базовому уровню.
* **Web Audio требует CORS.** Обе станции заголовки отдают; если перестанут —
  вторая попытка идёт без CORS, и пульс бьётся ровно, честно говоря, что музыки
  не слышит.
* **Уведомление приглушает музыку** на длину сигнала, плавно в обе стороны.
* Радио не включается само: музыка от одного открытия вкладки — это то, что
  закрывают не глядя. Выключение рвёт соединение, а не ставит на паузу.

## 7. Уведомления и звук

Уведомления рождались только в опросе объёмов и только на вход и закрытие.
Взятая цель, стоп и отработка звучали, но не показывались. Теперь уведомление
есть у каждого звука; висит вверху по центру **графика**, а не окна.

Опознаватели событий общие у двух источников — опроса биржи и наблюдения за
состоянием сделки: кто заметит первым, неизвестно, и второй ничего не добавляет.

**Звук** опущен на октаву и стал вдвое тише. Звонкость давали не громкость, а
мгновенная атака (ухо слышит удар по ноте) и верхние гармоники: добавлены 30 мс
подъёма и фильтр выше 1400 Гц.

## 8. Мелочи интерфейса

* **Плашки графика** больше не вылезают на журнал. Они едут за ценой через
  `translateY`, а координата считается и для цены за краем экрана. Теперь у цены
  вне видимой части плашки нет вовсе, а холст обрезает всё, что за него вылезет.
  Меню плюсика у нижнего края раскрывается вверх.
* **Скринер**: точка состояния вместо общей пометки. Полая цветом акцента —
  заявка ждёт, залитая золотом — позиция набрана.
* **Журнал**: нажатие на строку открывает график сделки и увозит его к её
  времени.
* **Страница снимка**: знак NMNH вместо подписи, время по часам зрителя,
  узкая шторка.
* **Лендинг**: свечи фона чёрно-белые, как в терминале.
* С компьютера кабинет открывается терминалом, а не «Анализами».

## Обновление удалённого стола

Сайт собирается на Render из гита; на удалённом столе живут бекенд и бот.

```powershell
cd "C:\Users\Администратор\Desktop\WEEX\MENTOR"
git fetch origin main
git checkout origin/main -- backend/ core/
```

Через `Invoke-WebRequest` обновлять ненадёжно: `raw.githubusercontent.com`
кеширует файлы минут на пять и молча отдаёт старую версию. Если без гита никак —
адрес нужно строить по хешу коммита, а не по имени ветки.

После обновления бекенд перезапустить: комиссия считается в сопровождении, а оно
живёт в процессе.
