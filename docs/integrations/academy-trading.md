# Статистика торговли ученика в мини-аппе академии

Ученик учится в академии и торгует у нас. Эта ручка отдаёт академии его
собственные торговые цифры, чтобы у неё в отдельном разделе появился экран
«моя торговля»: сколько сделок, с каким итогом, на каких биржах.

Опознаётся человек теми же ключами, что и везде в связке: `tg_id` или
`weex_uid`. Как они попадают в базу и как устроен общий секрет, описано в
[academy.md](academy.md).

## 1. Запрос

```
GET https://api.nmnh.trade/api/academy/trading/summary?tg_id=123456789&days=30
X-Service-Key: <SERVICE_API_KEY>
```

| параметр | тип | по умолчанию | смысл |
|---|---|---|---|
| `tg_id` | int | один из двух обязателен | Telegram ID ученика |
| `weex_uid` | string | один из двух обязателен | UID счёта, в любом написании |
| `days` | int, 1..365 | 30 | окно: сколько последних дней считаем |
| `limit` | int, 1..50 | 10 | сколько последних сделок вернуть списком |

Ключ тот же, что у начисления монет: `SERVICE_API_KEY`. **Он живёт только на
сервере академии.** Из браузера мини-аппа ходить сюда нельзя: заголовок увидит
любой, кто откроет инструменты разработчика, и дальше чужой PnL достаётся по
одному номеру телеграма, который знает каждый, кто был с учеником в общем чате.
Правильная схема: мини-апп просит свой сервер, сервер идёт сюда.

### Верхние поля

| поле | смысл |
|---|---|
| `exists` | ученик у нас найден. `false` - записи ещё нет, это норма для новичка |
| `has_trades` | за окно есть хоть одна закрытая сделка |
| `has_keys` | подключён хотя бы один торговый счёт: человек может торговать прямо сейчас |
| `first_login_at` | `null` - в кабинет ни разу не заходил. Повод позвать его туда |
| `created_via` | откуда взялась запись: `bot`, `site` или `academy` |
| `since` | левая граница окна, UTC |
| `source` | всегда `terminal_journal`, см. раздел 4 |
| `truncated` | сделок за окно больше пяти тысяч, сводка посчитана по свежим |
| `cabinet_url` | куда вести кнопкой «подробнее» |

### Числа сводки

Все деньги в USDT, доли - числом от 0 до 1 (`win_rate: 0.666667` это 66.7%).

| поле | как считается |
|---|---|
| `wins` / `losses` / `flat` | сделки в плюс, в минус и ровно в ноль |
| `win_rate` | `wins / (wins + losses)`. Нули в знаменатель не идут: выход в ноль не победа и не поражение |
| `gross` / `drawn` | сумма плюсов и сумма минусов по модулю |
| `net` | итог за окно, уже за вычетом того, что съели минусы |
| `fees` | комиссия обеих ног, отдельно от `net` |
| `profit_factor` | `gross / drawn`. **`null`, если убытков не было** - делить не на что |
| `expectancy` | средний результат одной сделки |
| `volume` | оборот: вход и выход вместе, с них биржа берёт комиссию |
| `avg_r` | средний результат в риске (риск - расстояние до стопа на объём). `null`, если стопы не проставлены |
| `drawdown` / `drawdown_pct` | худшее падение накопленного итога и его доля от пика |
| `hold_minutes` | сколько в среднем держал сделку |

Эти же формулы считает раздел аналитики нашего кабинета. Совпадение намеренное:
один человек видит свои цифры на двух экранах, и разный винрейт читался бы как
сломанные данные.

## 3. Пустые состояния

Ручка не отвечает `404` и не ругается там, где ничего не случилось. Четыре
случая, и все возвращают `200`:

| что показать | как узнать |
|---|---|
| «Ты ещё не с нами» - приглашение в кабинет | `exists: false` |
| «Счёт не подключён» - как подключить ключи | `exists: true`, `has_keys: false` |
| «Сделок пока нет» - приглашение открыть терминал | `has_trades: false` |
| Полная сводка | `has_trades: true` |

Во всех случаях `summary` заполнен нулями, а не отсутствует: рисовать плитки
можно, не проверяя каждое поле на `null`.

### Коды ответа

| код | причина |
|---|---|
| 200 | ученик найден, не найден или без сделок - смотри `exists` и `has_trades` |
| 400 | не передали ни `tg_id`, ни `weex_uid` |
| 401 | неверный `X-Service-Key` |
| 422 | `days` или `limit` вне допустимых границ |
| 503 | `SERVICE_API_KEY` не задан на бэкенде - интеграция не настроена |

## 4. Три вещи, о которые легко споткнуться

**Это торговля через наш терминал, а не вся торговля на бирже.** В журнал
попадает то, что открывал и закрывал терминал: там известны цены, комиссия и
итог. Сделки, сделанные руками в приложении биржи, сюда не попадут. Ученик,
который торгует и там и там, увидит у себя меньше, чем на бирже, и без подписи
на экране сочтёт, что цифры врут. Достаточно строки вида «по сделкам через
терминал NMNH». Поле `source` на это и заведено.

**Дни считаются по UTC.** `by_day` группирует по календарной дате UTC - так же,
как календарь прибыли в кабинете. Если мини-апп рисует дни по местному времени
ученика, границы разъедутся и вечерние сделки уедут на соседнюю клетку. Либо
показывайте UTC, либо пересчитывайте и там и там одинаково.

**Окно сдвигается, а не привязано к календарю.** `days=30` это последние
тридцать суток от момента запроса, а не текущий месяц.

## 5. Что разумно показать на экране

Порядок по убыванию пользы для ученика:

1. Крупно: `net` за окно и `win_rate`. Это то, ради чего экран открывают
2. Полоса дней из `by_day`: видно ритм и серии
3. Плитки поменьше: `trades`, `profit_factor`, `expectancy`, `drawdown`
4. `top_symbols` и `by_exchange` - чем и где торгует
5. `last_trades` списком и кнопка на `cabinet_url` за полной историей

Суммы разных бирж не складывайте в одну строку: у каждой свой счёт, и общий
итог по ним - это не число, а каша. Общий `net` в сводке уже посчитан правильно.

## 6. Проверка

Живость бэкенда: `GET https://api.nmnh.trade/api/health`, без авторизации.

Сама ручка с ключом:

```bash
curl -s -H "X-Service-Key: $SERVICE_API_KEY" \
  "https://api.nmnh.trade/api/academy/trading/summary?tg_id=123456789&days=30" | jq
```
